# JSONL core speed closure: complete implementation and benchmark plan

Status: approved for implementation on 2026-10-29; implementation in progress. Source reviewed at `c744171`. This supersedes the incomplete “first experiment” recommendation in [step-3 research](jsonl-step3-research-20261029.md). Keep existing original benchmark inputs and outputs frozen for historical comparison.

## Correction to the research recommendation

The typed aggregation experiment **already exists** as [text-slice-and-compact-record](fixtures/jsonl-summary-text-slice-compact-record/README.md) and has a [15-pair, output-checked result](results/jsonl-text-slice-and-compact-record-paired-15.json). At 200k rows its artifact time was **0.712×** the original Guion program (95% interval 0.704–0.763), yet **2.569×** Python (2.365–2.706). Source results were 0.710× original and 2.624× Python. The variant changed both date extraction and aggregate representation, so the 28–29% improvement cannot be attributed solely to JSON copy-on-write. It proves that the original application shape imposes a material cost and that a large core gap remains after a more idiomatic representation. Recreating this variant or running another broad parser-only optimization as the first task would repeat completed work.

## Recommendation in full

Implement two complementary changes in one bounded sprint:

1. **Fix the general-purpose value and control-flow path.** Build a typed register/SSA execution tier for the actual JSONL hot functions, covering `Result`/`Option` tag tests and unwrap, `JsonTry*`, local/constant loads, arithmetic, branch, call/return, and host operations. Keep common chains inside that tier instead of crossing a generic bridge per operation. Use liveness to move values when their previous slot is dead and represent temporary `Result`/`Option` as tag plus payload until an observable/materialization boundary. Preserve exact fuel, cancellation, allocation-budget, error-span, side-exit and VM-continuation behavior. Begin with the already profiled functions; the mechanism must be generic and available to any eligible Guion function, with no workload-name special case.
2. **Fix avoidable aggregate copying and give Guion an idiomatic update path.** For unique JSON values, retain safe in-place mutation through the current `Arc::make_mut` path; for shared values preserve value semantics. Add an ownership-aware mutable map/record update operation or compiler lowering that lets a Guion program update a typed aggregate entry without repeatedly cloning a container and reboxing JSON fields. The existing compact-record program is the immediate use case. Keep JSON construction at the output boundary in the idiomatic lane. Do not remove copy-on-write from shared aliases or quietly change Guion's value semantics.

These are not two guesses to try sequentially. The measured original lane and compact-record lane need both: the former exposes JSON COW and generic VM traffic; the latter removes much of the JSON churn yet remains 2.57× Python. An isolated allocator swap, frame pool, another per-op bridge, or a JSON parser fast path is not the main plan: those have either a small measured ceiling or prior negative end-to-end results. Compile and startup cost must be measured in source mode, not hidden in artifact mode.

## Benchmark set for this stage

The early suite still serves **breadth and regression**: tiny source/startup, Richards control-flow/collections, nbody, Mandelbrot, HTTP, and lockfile auditor catch damage outside the JSONL path. Richards is already fast and does not stress JSON parsing, boxed `Result`/`Option`, nested JSON updates, or the measured 29.09 million allocator calls. It is not a useful speed-closure target. The original JSONL app remains the required historical end-to-end gate. Its algorithm is less idiomatic than Python's; it cannot, by itself, diagnose whether the remaining gap is program shape or core implementation. The compact-record variant must become a first-class performance lane because it has already separated a material application-level cost while retaining a 2.57× gap.

Add only these focused programs, with Guion and equivalent Python versions where a cross-language comparison is meaningful:

| New program | Exact work isolated | Required evidence |
| --- | --- | --- |
| `result-option-loop` | Repeated successful and failing `Result`/`Option` creation, `is_ok`/`is_some`, unwrap, branch, and function return over deterministic input; no file or JSON work. | Equal checksum/error behavior; instructions/row, actual allocation calls/row, VM/native share, paired time. This directly tests boxing and same-function control-flow lowering. |
| `json-field-extract` | Read fixed fields from already parsed JSON values, including absent and wrong-type fields; exclude file iteration and aggregation. | Equal extracted checksum/error counts; `JsonTry*` calls and allocation calls/record; paired time. This tests whether JSON/result chains stay within the new tier. |
| `aggregate-update` | Update `(service,date)` count/min/max over prevalidated events in three Guion forms: existing JSON state, existing compact-record form, and new mutable typed-entry form; one equivalent Python dict/list reference. | Equal sorted report; JSON COW copies, map/record copies, allocation calls/row, time. This isolates representation and mutation costs from parsing. |
| `jsonl-streaming-summary` | Full real application with parse, validation, allow-list, aggregation, and report, using the new idiomatic update path. | Exact oracle on normal, invalid, strict, denied/oversized resource cases; 20k/200k source and artifact time, RSS, allocations, output hash. |

Reuse [read-only](../core_north_star_sprint/profile-inputs/jsonl-read-only.gu) and [parse-only](../core_north_star_sprint/profile-inputs/jsonl-parse-only.gu) as **diagnostic controls**, not a repeated optimization campaign. Keep the existing compact-record variant unchanged as the bridge between historical and new paths. A single source-level ablation that holds the aggregate representation fixed while changing only `text_chars` to `text_slice` is needed to divide the already observed 28–29% gain; this can be measured in the focused aggregate program, not another full-suite cycle.

## Execution and acceptance

Build the four new fixtures and their exact-output oracles **before** changing production code, and freeze source/input hashes. Implement both core changes as one coherent branch of work with correctness checks at each integration boundary. Use the existing healthy container, cached toolchains, sequential builds and trials, and no Docker/Colima lifecycle action. The same harness runs all focused programs and the four historical JSONL lanes in one final randomized paired cohort; only a failed correctness check or noisy result triggers a targeted repeat. Record all run orders, binary/source hashes, inputs, CPU/RSS, compiler time, allocator counts, and output checks. Re-run the early breadth suite once as a regression guard, not on every internal edit.

**Success requires both:** (a) the original historical JSONL application meets its already declared four-lane paired 95% upper Guion/Python ratio below 1.0, and (b) the idiomatic full application meets the same gate without a regression in short-source startup or the unrelated holdout. Focused programs must show that the intended mechanisms actually removed allocations/copies or tier crossings; speed results alone cannot explain cause. If original parity remains open while the idiomatic lane passes, report that distinction plainly and keep the historical gate open. If neither reaches parity, retain only changes with clear, reproducible benefits and state the remaining measured cost, without relabeling the target or extending the sprint through another sequence of speculative passes.
