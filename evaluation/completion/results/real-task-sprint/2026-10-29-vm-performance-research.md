# Guion runtime performance: historical lessons and next path

**Purpose.** Connect the measured Guion gap to established VM/compiler findings and choose the next implementation steps. This memo uses primary research and current branch evidence; it does not claim that historical results predict Guion's exact speedup.

## What Guion measures now

The fresh release build and output-checked 15-pair cohort show that the earlier nested-map copy cost is closed in the current source: at 200k rows, 392,762 map updates were in place and zero map copy-on-write clones were recorded. That cohort still places the current candidate at 3.85x Python in uncached source and 3.94x in artifact execution. The runtime profile reports 61,476,177 VM instructions, 3,770,554 frames, and zero native-compiled functions. `Load` (17.8M), `Store` (6.0M), conditional branches (4.2M), calls (3.6M), and result/option operations are prominent. This is evidence of a large interpreter path; it is not yet a hardware branch-miss profile.

The allocation-reservation candidate preserved exact budget outcomes but did not improve timing: all 15-pair intervals include parity at both sizes, with unchanged 9,699,328-byte Guion peak RSS. It was removed and its report retained. This is a useful falsification: a high count of accounting events alone did not establish that atomics were the causal bottleneck.

Evidence: `evaluation/development/core_cost_closure/results/jsonl-allocation-reservation-paired-15.json`, `evaluation/development/core_cost_closure/results/jsonl-closure-rebuilt-smoke-3.json`, and the sprint ledger.

## What prior VM work teaches

1. **Interpretation dispatch can be a structural cost.** Ertl and Gregg measured a high fraction of indirect branches in efficient interpreters and showed that prediction behavior can materially affect runtime. This supports measuring Guion's dispatch path directly; it does not prove that Guion's current bottleneck is hardware branch misprediction. [Ertl and Gregg, *The Structure and Performance of Efficient Interpreters* (2003)](https://jilp.org/vol5/v5paper12.pdf)
2. **Reduce dispatch before assuming every bytecode needs a full JIT.** The Vmgen work studies threaded code, stack caching, and superinstructions as separate interpreter optimizations. A profile-selected fused instruction sequence is a bounded, artifact-compatible experiment for Guion's frequent `Load`/`Store`/branch/call patterns. [Ertl et al., *Vmgen—a generator of efficient virtual machine interpreters* (2002)](https://onlinelibrary.wiley.com/doi/10.1002/spe.434/abstract)
3. **Dynamic runtimes need a fast common path and a correct general fallback.** Meta-tracing and self-optimizing interpreter research uses runtime feedback and guards to specialize stable paths, while preserving slower general behavior for uncommon cases. It also shows that object/data layout and interpreter organization can matter as much as the JIT itself. [Bolz and Tratt, *The Impact of Meta-Tracing on VM Design and Implementation* (2015)](https://tratt.net/laurie/research/pubs/html/bolz_tratt__the_impact_of_metatracing_on_vm_design_and_implementation/)
4. **Compilation tiers must match workload lifetime.** A baseline tier can provide useful speed before an optimizing tier is worthwhile, but repeated transitions between native code and the interpreter can erase gains. Guion must report cold source, artifact startup, and sustained work separately, and must keep helpers on a stable tier where possible. [Izawa, Masuhara, and Bolz-Tereick, *Two-level Just-in-Time Compilation with One Interpreter and One Engine* (2022)](https://prg.is.titech.ac.jp/papers/pdf/pepm2022.pdf)
5. **Optimizer overhead is not execution speed.** The 2026 GenExtension study reduces tracing and deoptimization-metadata generation time but reports nearly unchanged total execution time. Guion should measure end-to-end latency and memory for each tier, not count fewer compiler operations as a runtime win. [Izawa et al., *Generating Interpreter-Specific Tracers for Meta-Tracing JIT Compilers* (MPLR 2026)](https://2026.ecoop.org/details/mplr-2026-papers/5/Generating-Interpreter-Specific-Tracers-for-Meta-Tracing-JIT-Compilers)
6. **Keep uncertainty attached to every claimed gain.** Benchmark repetition should be spent where the uncertainty is, and small differences need effect-size intervals. Guion's 15-pair no-win allocation experiment is correctly rejected rather than promoted from a profile or one fast run. [Kalibera and Jones, *Rigorous Benchmarking in Reasonable Time* (2013)](https://kar.kent.ac.uk/33611/)

## Research-informed implementation order

**1. Improve attribution.** Add optional dynamic bytecode transition counts and loop-hotness counts to the runtime profile, then identify the frequent sequences and hot regions in the unchanged JSONL application and an unrelated holdout. Keep profiler clocks off by default. Where the container supports it, collect hardware counters as supporting evidence; do not make availability of a system profiler a prerequisite for implementation.

**2. Test internal superinstructions first.** Use the measured sequences to try a small set of fused dispatch paths in an ephemeral executable representation. Keep serialized artifact format unchanged. Every fused path must preserve the original guest instruction fuel count, cancellation poll behavior, error span, stack effects, allocation charges, and VM fallback. Run same-build paired source/artifact trials and retain only a statistically supported result. This is a measured implementation step, not an assumption that superinstructions alone close the 3.8x gap.

**3. Build the mixed-value hot-loop bridge if dispatch remains dominant.** Extend the existing Cranelift backend in stages: one real helper-call fixture, then one hot loop from the unchanged JSONL program. Keep `Value` ownership and runtime operations behind explicit helper boundaries; retain VM fallback/deoptimization for unsupported types and unstable paths. Do not bounce between tiers on every helper call. Preserve host errors, capabilities, exact instruction/allocation budgets, cancellation, and trace/error reporting. Record compile time, code size, cold latency, steady-state latency, and RSS.

**4. Keep HTTP as an independently measured cost.** The existing direct bytes-to-JSON route improved the 1MiB source case but small 64KiB typed source remains slower than same-build legacy. Re-measure the same executable with source/artifact and phase-separated response conversion before changing that path; do not infer the fix from the JSONL VM profile.

**5. Use two acceptance gates.** Require output and policy equivalence for every lane. Require paired intervals for performance; report source, artifact, cold startup, steady state, and peak memory separately. Keep the JSONL/Python gate open until both frozen sizes pass. Keep HTTP open until its controlled small-payload lane closes without hiding a larger-payload regression.

## Main conclusion

The current evidence does not support another isolated allocation or JSON fast path as the answer. The measured residual points to Guion's execution engine: too much bytecode interpretation and repeated frame/control-flow work, with mixed-value JSON and host operations keeping the current numeric JIT from compiling the application path. The next decisive path is profile-selected dispatch reduction followed, if needed, by a hot-loop native bridge with a general VM fallback. That is compatible with the north-star emphasis on a useful agent language: improve real programs, keep startup visible, and preserve understandable policy and error behavior.

## Follow-up evidence — 2026-10-29

The next two profile-selected VM fusions (Store→Load and Not→JumpIfFalse) were tested with exact guest fuel and error behavior. Their paired intervals included parity; the 20k artifact lane regressed for Store→Load. Both implementations were removed. The feature-gated mixed-Value bridge then compiled 11 functions and reduced 200k VM instructions from about 61.5M to 52.0M, but the 15-pair candidate was 2.3–4.5% slower than its immediate pre-bridge build, depending on lane. Disabling it by default restored a measured 7–8% win over that predecessor. Reusing the bridge callback's temporary argument storage did not recover a win. A separate borrowed-`HostOpContext` instruction experiment also failed confirmation: all 20k/200k source and artifact paired intervals included parity, so its changes were removed.

This narrows the diagnosis: fewer VM instructions do not automatically make Guion faster when native code calls back through a per-operation mixed-Value trampoline. Further micro-fusion or allocation-accounting experiments are not justified without new causal evidence. The next engine experiment should compile a stable hot region or function tier that keeps execution in one tier across its calls and uses direct native lowering for its common path, with checked VM side exits for unsupported values and operations. The generic VM remains the fallback. This is a direction to test, not a claimed fix; acceptance requires end-to-end paired speed and the full policy/correctness suite.

The literature is consistent with this staged approach. [PEP 659](https://peps.python.org/pep-0659/) describes specialization in a small instruction region with cheap adaptation and deoptimization, including gains without machine-code generation. [Are We Fast Yet?](https://doi.org/10.1145/2989225.2989232) evaluates common language abstractions over a varied suite rather than treating one workload as a universal ranking. [Deegen](https://arxiv.org/abs/2411.11469) reports an optimized interpreter and a low-startup baseline JIT, illustrating a tier that can help before a more expensive optimizing JIT pays back. These results guide design choices; they do not predict Guion's outcome.

The HTTP result remains independent. Direct checked bytes-to-JSON helps large payloads; the 64 KiB uncertainty is concentrated in uncached source compilation, where the typed import closure currently takes longer to compile. Cached-source and artifact lanes are near parity. The source compiler/import path is therefore the appropriate target for that lane.
