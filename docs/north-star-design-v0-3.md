# Guion north-star design v0.3

Date: November 3, 2026. Status: approved direction from the architect. Builds on and supersedes [v0.2](north-star-design.md) (October 22, 2026), which is kept unchanged as the historical record. Read with `language/spec.md`, [status](status.md), and checkpoint [`guion_checkpoint_v1_50_ecosystem_direction.md`](guion_checkpoint_v1_50_ecosystem_direction.md).

## Goal

Guion is a general-purpose programming language built to replace Python. It should be better than Python at writing, checking, changing, running, and shipping software, across the same range of work Python covers today. That requires its own wide standard library, its own package ecosystem, and its own public releases.

Assistants recommending Guion over Python is one sign of progress. It is not the ceiling of the goal, and Guion is not limited to a few task classes. Anything Python can do that Guion can't yet do is a gap on the work list. It is not a reason to send users back to Python.

## What changes from v0.2

| v0.2 | v0.3 |
|---|---|
| Win a credible recommendation across several project classes; name the tasks where Python is still better. | Replace Python as a general-purpose language. Places where Python is currently ahead go on the work list as gaps, not as concessions. |
| The managed CPython sidecar is the dependency and ecosystem path. Use uv's resolver; don't build a competing one. | The Python bridge is frozen as an optional feature. Guion gets its libraries from its own standard library and its own packages. |
| Registry services are deferred "as evidence requires." | Package publishing and a hosted registry are on the current roadmap. |
| First distribution: the current macOS arm64 host. | A public release on every validated target, with a written stability policy. |
| Python's tooling is the comparison baseline. | Python stays the comparison baseline, now as a competitor. Comparisons are Guion-native against Python-native: Guion arrays against NumPy, Guion's HTTP server against Python's, and so on. |

## What carries forward from v0.2

These hold unchanged:
- One `guion` command that covers the whole project lifecycle.
- Stable diagnostic codes with repair guidance.
- Human and JSON reports that describe the same result.
- Indentation syntax and inferred local types.
- Arbitrary-precision `Int`, explicit `Float64`, and immutable collection values.
- `Option` and `Result`.
- One typed lowering path and one runtime semantics.
- Bounded structured concurrency.
- Capability grants that deny by default.
- Reproducibility treated as three separate claims: resolution, artifact bytes, and behavior.
- Versioned external contracts.
- Honest, paired, output-checked measurement.

Learning from Planes, Liminate, and Decan still applies. So does the rule against application-specific shortcuts in the runtime.

## Python bridge: frozen

The `python-interop` build feature stays as it is today: off by default, and never touched by the core build. Its existing tests keep passing. From here on:
- No more optimization or feature work on the bridge.
- Bridge results are not cited as evidence of Guion's ecosystem or speed.
- Removing it later, or keeping it as a tool for porting Python code, is a separate decision. This document does not schedule it.

## Ecosystem architecture

### Standard library: wide, native, versioned with the compiler

The standard library ships with each compiler release and is versioned with it. Speed-critical work is implemented natively in the Rust runtime, behind typed host operations, which is where the measured speed wins come from. The interface is written in Guion and documented through `guion doc`.

**Scope rule.** Stable protocols, file formats, and operating-system services go in the standard library. Domains that change quickly ship as first-party packages so they can release on their own schedule.

**Current modules** (verified at `e70617a`, `language/stdlib/`): calendar, cli, collections, crypto, csv, fs, http, http_types, json, jsonl, semver, sqlite, text, time, toml, types, unicode.

**Wave 1: systems, text, network.**
- Processes and subprocesses, paths, environment, signals, a full filesystem API, temp files.
- Regular expressions, base64/hex, URL parsing, character encodings.
- An HTTP server, TCP/UDP sockets, TLS, WebSockets.

**Wave 2: data and runtime.**
- Decimal, math/statistics, random numbers.
- Compression: gzip, zip, tar.
- YAML, XML/HTML parsing.
- Logging.
- Asynchronous I/O that fits Guion's existing structured concurrency.

**Later waves** cover what remains of Python's standard library, judged by what real Guion programs need. Examples include templating, email/MIME, and image formats.

Each module needs:
- conformance cases
- documentation generated by `guion doc`
- capability declarations where it touches the outside world
- a measured comparison with Python's equivalent wherever speed matters

### Native arrays and numerics

NumPy and pandas are the biggest part of Python's ecosystem advantage. Guion builds its own answer instead of borrowing theirs:
- typed n-dimensional arrays with fixed-width element types
- vectorized native kernels
- views that avoid copying
- parallel execution on the existing bounded workers

Data frames come after that, built on the arrays. The core array type belongs in the runtime and standard library. A data-frame package may ship first-party so its API can change faster. The headline benchmarks are against NumPy and pandas on equivalent workloads.

### Package system and registry

The foundation already exists. At `e70617a`, `crates/cli/src/native_packages.rs` provides:
- library manifests with name, version, entry, exports, and dependencies
- `guion add NAME --path PATH` and `guion add NAME --url URL --version VERSION --sha256 HASH`
- `guion update`
- `guion package --library`
- a dependency graph checked for cycles
- lock format 2, holding each package's content SHA-256
- a managed cache in `.guion/packages`
- `pkg:<name>/<path>` imports that resolve only through the lock

**What's missing (verified absent at `e70617a`):**
- Version ranges. `requirement_version` and `validate_exact_version` accept exact versions only.
- A resolver that picks versions within ranges.
- A `publish` command. There is no `publish` branch in `crates/cli/src/main.rs`.
- A registry or package index. No registry code exists in `native_packages.rs`.
- Dependency identities in artifact metadata. `docs/reference.md` lists this as not yet recorded.

**What it needs, in order:**
1. **Version ranges and resolution.** Semver ranges in `[dependencies]` (`std:semver` already exists), a resolver with clear explanations when no solution exists, and `guion add NAME` resolving from the registry by default.
2. **Library projects.** `guion new --lib`, a public-API surface checked by `guion check`, and per-package docs generated with `guion doc`.
3. **Publishing.** `guion publish` validates the manifest, runs tests, packages the source, records the content hash, and uploads. Published versions can be yanked but never deleted or replaced.
4. **The registry.** An HTTP index plus content-addressed storage, with name ownership, authenticated publishers, and a public log of each version's content hash.
5. **Capability declarations.** Each package declares the capabilities it uses: network hosts, file roots, environment variables, processes. Guion's existing static capability inspection checks the code against those declarations, and the lock records them. When an update asks for new capabilities, the person adding or updating it must approve. Python's package system offers nothing like this, and it is part of the design direction.
6. **Artifact identities.** Built artifacts record exactly which package versions and hashes went into them.

### First-party packages

These are packages the Guion project maintains and publishes to the registry, released on their own schedule. The first candidates:
- a web framework built on the standard-library HTTP server
- the data-frame layer
- a richer CLI toolkit
- database drivers beyond SQLite

They show what good Guion code looks like, and they populate the registry from the first day.

### Release and stability

The first public release on the roadmap is **0.2.0**:
- installers for macOS ARM64 and Debian 12 ARM64 and x86_64
- a written stability policy
- the registry live, with the first first-party packages on it

The current `v0.1.0-preview` is a Linux-only pre-release with no macOS package.

The stability policy covers:
- source compatibility within a 0.x minor series
- every runtime continuing to read all earlier artifact formats; it reads 14–48 today
- a deprecation period before anything is removed
- how library packages are distributed

Regular releases follow. Release-target builds run locally, or on demand, given the GitHub Actions budget.

## Roadmap

1. **Done.** This design document and checkpoint v1.50.
2. **Two parallel tracks:** the package system and registry (items 1–6 above), and standard library Wave 1.
3. Native arrays and numerics, then data frames.
4. Public 0.2.0 release with the registry live and the first first-party packages.
5. Further standard-library waves and first-party packages on a regular release schedule.

## Evidence policy

The v0.2 standards stay in force:
- Measurements are paired, output-checked, and reported with intervals.
- Every result gets reported, including losses.
- Claims are limited to what was actually measured.

What changes is the framing. A loss to Python is a gap with a work item attached, not a scoping decision. If an architecture choice can't produce a competitive result, the architecture changes. The bar and the goal stay where they are.

## Open design questions

These are tracked in checkpoint v1.50 and get decided during steps 2–4:
- Registry hosting and publisher authentication.
- Whether packages are distributed as source or as artifacts.
- Element types and integer widths for arrays.
- The exact stability-policy promises.
- Name ownership and naming conventions.
- Packaging the macOS release.
- Where each module falls between the standard library and first-party packages.
- An async I/O model that works with bounded parallel groups.
- The long-term fate of `python-interop`.
