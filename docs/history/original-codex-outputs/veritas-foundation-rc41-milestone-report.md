# Veritas RC41 milestone report

**Result:** the current-host package now verifies its recorded files before it runs. Pure-Veritas and Python-assisted bundles relocate on macOS ARM64, and a package altered after creation is rejected before app output.

## What changed

- Added `veritas verify-package DIRECTORY`; every generated `./run` checks target, artifact/runtime/resource hashes, and managed Python runtime, resolver, and lock identities before launching.
- Prevented the Python sidecar from writing generated bytecode into the packaged interpreter. This keeps its recorded runtime hash valid across repeated launches.
- Added tests proving that corrupt data and Python runtime files are rejected. Kept repeat-launch coverage for moved packages.
- Expanded the release archive to include task briefs, evaluation protocol, recorded JSON results, runnable acceptance tests, known-workload runner, language reference, and milestone checkpoints.

## Verdict and limits

This is an end-to-end delivery proof for a narrow sample on one host. It does not establish that an assistant should recommend Veritas over Python. The package hashes are unsigned and do not authenticate a publisher. The offline resolver cache and generated Python virtual environment are not independently hashed. Arbitrary native-wheel dependencies, their full shared-library closure, and Python license collection remain open. Linux, Windows, and clean-machine installation remain untested. The recorded tasks are author-run; no independent builder or assistant-choice comparison supports a recommendation yet.

The recommendation gate stays open. The next work is dependency provenance and license reporting, stronger verification or reconstruction of installed Python environments, broader target coverage, and the preregistered independent task evaluation.
