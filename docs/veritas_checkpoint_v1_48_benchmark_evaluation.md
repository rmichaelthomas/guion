# Veritas checkpoint v1.48: benchmark evaluation

Date: October 22, 2026. Status: evaluation complete; native execution remains the next engineering priority.

## What was checked

The three original uploads were inspected and the two Python scripts were copied to a temporary directory before syntax checks and execution. `veritas.py` fails parsing at line 113 (`def peek(() -> Token:`). `veritas_ultimate.py` passes its self-check for the one hard-coded calculation: numbers 6 through 10 sum to 40. Its “VM” traverses AST nodes directly. Its C exporter returns a fixed source template, independent of the parsed program; the script only writes `.c` and `.h` files and does not compile them. A separate C harness did compile and call that template, returning `0,40,63,1` for its input probes. This verifies that the static C functions are callable, not that Veritas emits native code or has an FFI pipeline. Upload hashes and detailed outcomes are recorded in `evaluation/results/veritas-uploaded-starter-verification.json`.

No Pystone, Richards, n-body, or Mandelbrot benchmark source files were attached or present in the workspace. The local environment does not have `pystone`, `pyperf`, or `pyperformance` installed. A dependency-free Mandelbrot escape-time kernel was therefore authored as a comparable translation, copied with its manifest into a temporary directory, checked, built as a format-22 artifact, and run against Python 3.14.7 and an independently compiled C reference. Each implementation printed `155052` and `1608`. The workload is 96 by 64 points with an 80-iteration ceiling; it is not the Computer Language Benchmarks Game source.

## Results on this host

The runner uses two warmups and 15 fresh-process samples per implementation. Each sample includes process startup; Veritas source execution also includes parsing, typechecking and bytecode compilation. The artifact run loads saved bytecode. C compile time is measured separately.

| Implementation | Median | p95 (nearest rank) | Relative to Python median |
|---|---:|---:|---:|
| Veritas source | 163.0 ms | 164.2 ms | 3.8× slower |
| Veritas bytecode artifact | 162.3 ms | 164.0 ms | 3.8× slower |
| Python 3.14.7 | 42.5 ms | 43.7 ms | baseline |
| C, Clang `-O3` | 3.9 ms | 4.2 ms | 10.9× faster |

The bytecode artifact does not materially reduce runtime in this workload because it remains interpreted bytecode. Native C is only a comparison ceiling; it is not generated by Veritas. Raw timing samples, host metadata, artifact size, and separate compile times are in `evaluation/results/famous-benchmarks-rc71.json`. This is a single numeric workload on one Apple Silicon host, not a general performance result.

## CPU concurrency check

A second matching workload runs four independent integer loops through Veritas `parallel_map` and Python serial, thread-pool, and process-pool modes. All return the same four values. The local Python 3.14.7 reports its GIL as enabled. At 20,000 iterations per task, Veritas parallel-map source/artifact medians were 139/149 ms; Python serial/thread/process medians were 61/59/162 ms. At 200,000 iterations per task, Veritas needed a scratch manifest with a 1 GiB cumulative allocation ceiling because the default 256 MiB ceiling returned `R_ALLOCATION_LIMIT`; with that override, Veritas source/artifact medians were 1,411/1,423 ms and Python serial/thread/process medians were 86/87/160 ms.

These are process-level comparisons and the process-pool results include worker startup. They show that Veritas parallel-map returns deterministic ordered results, but this CPU loop does not make Veritas faster than serial Python or Python processes. The larger workload also shows that its allocation policy can stop CPU-bound programs before memory pressure is reached; the ceiling is configurable, though a higher limit is not a performance fix. This probe does not measure CPU-core utilization and is not evidence of a Veritas concurrency advantage.

## Corrections to the proposed benchmark claims

- Pystone is historically known, but it is not a current universal gate. Python's own 2.4 release notes called it “not a particularly good benchmark,” and the pyperformance project removed it in its initial 2016 release.
- Richards is a real benchmark in the current `pyperformance` suite. That does not substantiate the claim that it is a universal CPython-core test. Its object mutation, inheritance, linked packets, and dispatch are beyond the current Veritas subset.
- n-body has a named Computer Language Benchmarks Game implementation. Its source uses `math.sqrt`, mutable list/tuple state, and repeated in-place numeric updates. Veritas currently has no `sqrt` built-in, mutable collection or record fields, or native calls; routing each square root through the Python sidecar would not test native numeric execution.
- Mandelbrot can be represented by the current scalar numeric and loop subset, so it is the cleanest direct probe today. Passing this small translation establishes arithmetic and loop parity for this case, not Python compatibility.
- The current CPython implementation has optional free-threaded builds as of Python 3.13. The standard build still uses the GIL for Python bytecode; some extension modules can re-enable it in a free-threaded build. The concurrency question must be benchmarked against a current Python setup, not summarized as a permanently fixed binary limitation.

## North-star consequence and next build action

The existing bytecode engine currently misses the north-star performance hypothesis on both scalar numeric work and CPU parallel work: it is slower than CPython here and far behind optimized native C. The next engineering work should prototype a real native backend for typed numeric loops, with an explicit backend boundary and VM fallback for unsupported programs. Its acceptance gate is output parity on this Mandelbrot kernel plus existing language conformance, then the same benchmark matrix against Python and native C. The backend must not silently change integer, float, error, source-location, resource-limit, or packaging semantics. Before expanding it to general code, profile object-heavy work such as Richards and stateful application workloads to decide which value operations need native representation. Add a separate allocation-lifetime policy check so a bounded memory ceiling does not unexpectedly block long numeric loops through cumulative temporary-value accounting.

This checkpoint does not claim the north star is met. The reproducible test harness and this failure analysis establish the next backend decision from observed evidence rather than a presumed native pipeline.
