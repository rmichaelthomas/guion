# Guion real-task and Richards sprint

## Intent

Move Guion toward being an easier, faster, more compelling choice than Python for agents doing everyday work. Connect three forms of evidence that have so far been separate: using Guion from a clean installation, running correct implementations of real tasks, and choosing a language after trying both. Preserve the real AllHereHTML builder as a regression workload, use it to investigate text processing and developer experience, and improve Richards only after identifying a causal runtime cost. Keep Guion private and in active development.

## Starting evidence

- The latest output-checked, fresh-source Richards cohort measured 46.00 ms for Guion and 67.43 ms for pinned CPython 3.14.7 on macOS ARM64 (Guion/Python ratio 0.685). The same report records peak RSS; memory measurement is not an open blocker.
- The host CPU profile has 98 target-process samples, with 92 stacks containing `NativeCode::invoke`. Fifty-nine terminal samples end in unsymbolicated generated code. It rules against VM dispatch as the leading observed cost, but does not determine the branch-versus-allocation split within generated code.
- The D4 Codex choice run recorded 3/18 Guion choices with product information and 0/18 with the brief alone. Both network choices were for the *same* service-health brief; the third was for lockfile auditing. The run measured before-use opinions from one model, not implementation quality or a causal effect of product copy.
- The repo already contains nine Guion regression applications, older matched Python references, and acceptance fixtures. The current Guion applications have passed source-free relocation checks on the validated targets. Reuse and refresh these assets; do not restart the applications from scratch.
- The separate `/Users/rmichaelthomas/allherehtml/guion` project contains a Guion-native builder and validator for a real site. Its saved QA records 77 checked functions, 19 passing Guion tests, a successful generated-page build, and an atomic write. The builder reads a template and three Guion examples, substitutes and escapes text, validates the document, and writes the result without Python interoperability. The reported text-efficiency and library-ergonomics concerns are hypotheses to measure, not established timing regressions.
- The shared VM-core refactor merged into `main` at `9d57434`. It moved the bytecode VM into a portable core and added a Wasm adapter; the native JIT path was unchanged. AllHereHTML commit `a6f3291` subsequently activated the shared VM and a single-file browser compiler in its playground. Its older limited VM remains historical. Do not duplicate either integration in this sprint.
- The validated target matrix is macOS ARM64 and Debian 12 GNU/Linux on ARM64 and x86_64 with glibc. Installable host archives and an installer already exist; the current getting-started path assumes a source checkout and Rust/Cargo.

## Product and workflow requirements

1. **Clean install.** Make a repeatable installation path for a prebuilt Guion CLI on each already validated target. A recipient starting without Rust, Cargo, Python, or uv must be able to install the core package, create a project, check it, run it, and remove the installation. Reuse the existing package and installer where possible. Record archive identity, installed bytes, commands, results, and any host prerequisites.
2. **Matched real tasks.** Refresh the existing Guion and Python implementations against the same frozen briefs and acceptance fixtures. Start with service-health digest, lockfile auditor, and webhook replay. The first two are the distinct briefs that received Guion choices; webhook replay is a Python-favored comparison with network and state requirements. Use the existing code and fixtures as inputs, but check that old Python references and their dependencies still represent the current briefs. Expand to the remaining six briefs after the three-task method passes its acceptance and fairness checks. Where an implementation needs Python interoperability, label it and include that cost; do not describe it as Python-free.
3. **AllHereHTML regression and text study.** Bring a minimal, provenance-tagged snapshot of the Guion AllHereHTML builder, template, inputs, and correctness oracle into this repo's evaluation fixtures, pinned to the source repository commit. Rebuild and validate the same site after the VM-core merge and after relevant runtime or text changes. Check output bytes or a stable semantic oracle, rejection of unsafe page content, failure handling, and atomic-write behavior. Measure fresh-source build time, repeated build time, peak memory, and scaling across at least three document/input sizes. Profile string conversion, concatenation, replacement, scanning, and allocation outside timed lanes. Only then select a reusable text improvement, such as a builder, replacement primitive, or substring API, if the measurements support it. Keep the AllHereHTML application logic in Guion; any standard-library change must help more than this one application. Record the authoring friction in concrete terms: helper code needed for common operations, error-handling steps, API discoverability, and the amount of code that is application policy versus text plumbing.
4. **Complete task evidence.** For each matched brief, verify behavior before measuring speed. Report acceptance outcomes, clean setup and installation effort, first uncached source run, cached source run, packaged/artifact launch where supported, peak memory, delivered bytes, and intervention count. Time the same task boundary in both languages. Separate Guion compiler/runtime time from total wall time in diagnostic runs. Verify every timed output against the frozen oracle. Preserve failed and inconclusive runs rather than dropping them. The report must explain when a Python library supplies functionality Guion does not yet implement natively. Report AllHereHTML separately as a real-app regression; do not silently count it as one of the nine frozen briefs or claim Python parity without a matched current Python run.
5. **Evidence-led Richards work.** Add opt-in visibility for Guion's generated native code or perform controlled, output-checked experiments that isolate list copy/allocation work from branch/control-flow work. A host executable dSYM alone is not sufficient for JIT-generated functions. Avoid another privileged profiler dependency: host sampling may corroborate the finding, but the sprint must be able to reach a causal conclusion with repository-local instrumentation or controlled variants. Keep instrumentation off timed runs. Apply the smallest behavior-preserving change supported by the measured cost, then rerun Richards, the five short fresh-source gates, relevant conformance/acceptance tests, the AllHereHTML regression, and peak RSS. Preserve the post-refactor baseline and candidate in one randomized comparison. The stretch target is a fresh-source Guion/Python Richards ratio of 0.60 or lower on the pinned macOS cohort; a smaller verified gain is reported as such, never rounded into the target.
6. **Choice after use.** After the install and task evidence exists, run a small, frozen, post-trial agent study. Give the evaluator both working implementations, the same acceptance checks, and the same measured setup/performance facts. Use fresh related briefs rather than asking it to rejudge the exact programs it has seen. Record the choice and rationale for every trial. Run through one compact local harness with isolated model invocations and repository-local records; do not create visible Codex chats or extra worktrees per choice. Keep these results separate from D4's before-use results and make no causal claim from the difference between arms. Include an application-shaped text/HTML brief if the AllHereHTML comparison has a fair current Python reference; otherwise use its verified Guion result as context, not as a two-language choice trial.
7. **Documentation travels with changes.** Update README, getting-started, status/readiness, agent entry points, and relevant command or capability references in the same changes that alter behavior or evidence. The README's historical statement that CPU attribution is wholly unknown must be corrected to reflect the saved host profile. Keep all performance and platform claims tied to the current reports, not older snapshots. Documentation updates are routine completion work, not a separate optional workstream.

## Measurement and execution rules

- Work from the canonical `/Users/rmichaelthomas/guion` checkout on a new branch; keep scratch, tool caches, generated packages, and reports inside the repo. Use one Cargo target directory and existing local dependencies. Remove bulky transient scratch after the retained compact records are verified.
- Start implementation from `main` after the VM-core refactor merges and its CI result is known. Record the exact merge commit. Rerun a small correctness and performance baseline on that commit before comparing any sprint optimization; the older 0.685 Richards ratio is historical, not automatically the new baseline. Verify native source/artifact execution, shared VM-core conformance, Wasm adapter ABI, and the AllHereHTML browser smoke path against the merged implementation where supported. Do not modify the pending refactor branch or recreate its portable core.
- Preflight all required commands, dependencies, permissions, and target availability once before long runs. Use the working execution environment rather than cycling through known failing permission paths. Do not require root access for a sprint gate.
- Reuse the repository's existing randomized, paired, output-checked timing harness where it fits. Pin the Guion revision, Python version, target, runner profile, inputs, and package identities. Label OS page-cache state as uncontrolled; `--no-cache` bypasses Guion's source cache but does not make disk access cold.
- Keep acceptance and diagnostic runs outside timed lanes. Capture raw observations, median ratios, uncertainty intervals, and memory sampling method. Measure installation/setup separately from program execution so a faster runtime cannot hide slower delivery.
- The three-task pilot must pass before scaling to nine briefs. The nine-brief comparison is a planned part of this sprint, not an indefinite follow-up. If an existing reference is stale, repair the reference and its oracle before comparing timings.
- Keep language permissions runner-controlled. If the service-health or webhook trials show that exact-host grant discovery is a material source of errors or setup cost, specify and implement an auditable source/project declaration that `check` and `inspect --json` can compare with runner grants. A declaration must never grant network access by itself. Include the before/after setup evidence; do not add syntax solely because an earlier reviewer proposed it.
- Do not edit project-level `AGENTS.md` files. Use `python3` for Python commands.

## Deliverables and acceptance gates

1. **Install gate:** a prebuilt CLI installs and runs the core hello/check/test path without Rust/Cargo/Python/uv on each claimed target; archive hashes, sizes, removal path, and target-specific results are retained. A target that was unavailable is explicitly unverified, not passed.
2. **Task gate:** all three priority briefs pass their frozen acceptance cases in both languages, with equivalent outputs and error behavior. A full nine-brief matrix follows with the same rule. Every brief has a concise comparison of setup, runtime, memory, and delivered size, including limitations.
3. **AllHereHTML gate:** the pinned builder still produces and validates the expected site, including negative cases, after the VM-core merge and any sprint change. The text study reports timing, memory, scaling, and where time is spent; it makes a measured library/runtime improvement or names the concrete reason one is not yet justified. Any new API is tested on both the application and independent text cases. The authoring review lists specific friction and the smallest reusable fix, with before/after examples where a fix is made.
4. **Richards gate:** a causal profile or controlled experiment identifies the targeted cost; a change passes correctness, memory, the AllHereHTML regression, and the five short-source regression gates. The report gives exact current-versus-baseline and Guion-versus-Python ratios, including uncertainty. If the proposed change fails its gate, revert it and record the finding rather than retaining a regression.
5. **Choice gate:** the post-trial protocol, prompts, complete decisions, and counts are saved. Its report says which briefs changed an agent's recommendation and why, without treating a small sample as a general adoption verdict.
6. **Handoff gate:** README and current docs agree with the retained evidence; implementation, tests, reports, and documentation are reviewable together in a PR. The summary is plain English and states what improved, what did not, and the next largest measured gap.

## Boundaries

- Keep the repository and installable artifacts private during this sprint; it does not publish a release.
- The north star remains broader than any one benchmark. A Richards win cannot substitute for correct real-task results or a usable install path, and a positive choice count cannot substitute for measured correctness or performance.
- Do not infer a universal Guion-over-Python result from these named tasks, platforms, or agent trials.
