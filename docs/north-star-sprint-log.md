## Rulings

- Use Cranelift JIT rather than invoking the system C compiler at runtime. It emits machine code in the Rust process and keeps application launches independent of a user-installed compiler. Cost if wrong: runtime binary size and build time increase, and current-target JIT support needs broader packaging checks.
- Keep arbitrary-precision integers authoritative and use checked `i64` fast paths. Cost if wrong: overflow requires rerunning a pure function in the VM; eligible functions therefore exclude side effects and calls, and the fallback path is covered by a boundary test.
- Keep unsupported functions on the VM while the native subset grows. Cost if wrong: mixed workloads can still spend most time in the VM; backend eligibility and coverage must remain visible and benchmarks must include mixed and fallback cases.
- Keep native code behind the same fuel budget using bounded reservations. Cost if wrong: private reservations briefly reduce fuel visible to sibling workers, so reservations stay small and unused fuel is returned on every exit path. Exact single-invocation instruction-limit boundaries are tested.
- Allow native-to-native calls only through a statically checked acyclic call graph. Runtime call-depth limits are checked at each generated call; recursive functions stay on the VM. A fallback in a pure nested call returns to the VM with consumed fuel refunded before replay.

- Fifteen randomized fresh-process pairs measured 79.89 ms vs. 79.98 ms for the empty value (Guion/Python ratio **0.993**, 95% interval **0.979–1.019**) and 83.15 ms vs. 80.68 ms for the large value (ratio **1.043**, **1.004–1.050**). The relative payload penalty was **1.045** (**1.001–1.088**). All outputs matched expected byte counts.
- The zero-byte path is at parity in this run; the measurable gap grows with the payload. This points to payload-scaled work but does not attribute CPU among file reads, pipe transfer, frame parsing, and attachment conversion. The next optimization targets `read_exact`'s intermediate read buffer. See the [control report](../evaluation/completion/results/real-task-sprint/2026-10-28-python-bridge-startup-sizes.md) and [raw JSON](../evaluation/completion/results/real-task-sprint/2026-10-28-python-bridge-startup-sizes.json). The earlier single-size 5.1 MB cohort remains in the [separate report](../evaluation/completion/results/real-task-sprint/2026-10-28-python-bridge-startup-5mb.md).

## Python bridge frame-reader allocation and timing follow-up (2026-10-28)

- Changed `read_exact` to preallocate the known frame size and fill it with `readinto`, preserving short reads, clean EOF, and truncated-frame errors. The isolated 5,100,867-byte frame peak fell from 10,201,824 to 5,101,732 bytes.
- The 100,000-row NumPy/orjson workload measured 145.64 ms for Guion `Bytes` and 142.00 ms for package-backed Python; the paired ratio was 1.019 (95% interval 0.995–1.046). The no-op payload penalty was 1.031 (1.019–1.038). Independent-cohort bootstrap ratios for candidate/baseline were 0.987 (0.953–1.018) for the payload penalty and 0.999 (0.980–1.033) for the full application. No runtime speed change is established; all outputs matched.
- The next experiment tests a full-frame `read()` fast path, retaining `readinto` to assemble partial reads. The goal is to avoid zero-initializing the full frame when the buffered pipe can return it in one read. ## Python bridge direct-read fast-path experiment (2026-10-28)

- Tested returning a complete buffered frame directly from `read()`, with the `readinto` path retained for partial reads. Tests passed and the 100,000-row application outputs matched. The candidate measured 139.40 ms for Guion `Bytes` and 134.30 ms for package-backed Python; the ratio was 1.038 (95% interval 0.987–1.059). The no-op payload penalty was 1.034 (1.000–1.115).
- Independent-cohort bootstrap comparisons against the readinto-only run estimated 1.018 (0.967–1.043) for the full application ratio and 1.003 (0.975–1.072) for the payload penalty. Peak allocation was 5,101,212 bytes versus 5,101,732 bytes. No measurable benefit was found, so the fast-path code was reverted.
- A streaming-reader prototype for one 5.1 MB attachment failed the one-copy allocation bound: the buffered pipe returned fragments, requiring a mutable buffer followed by a copy to immutable `bytes` (10,203,084-byte peak). The prototype was dropped before being retained in the branch. Next, compare repeated bridge calls after the sidecar is running to measure per-call cost separately from process startup. See the [experiment report](../evaluation/completion/results/real-task-sprint/2026-10-28-python-bridge-direct-read.md), [application samples](../evaluation/completion/results/real-task-sprint/2026-10-28-python-bridge-direct-read-application.json), and [no-op samples](../evaluation/completion/results/real-task-sprint/2026-10-28-python-bridge-direct-read-startup.json).

## Python bridge repeated-call measurement (2026-10-28)

- Measured 1, 10, 100, and 1,000 typed calls in one Guion program, with the same Python function looped directly as the reference. Across 15 randomized pairs, ratios were 1.046 (0.984–1.068), 1.066 (1.035–1.078), 1.339 (1.303–1.386), and 4.131 (4.046–4.305), respectively. Every stdout/stderr matched the expected sum.
- The paired 1→1,000-call difference estimates 0.239 ms added per Guion call and 0.00019 ms for Python; their excess is 0.241 ms per added call (95% bootstrap interval 0.236–0.254 ms), positive in all 15 pairs. This includes loop execution and the entire bridge request/response path; component attribution remains open.
- Next, instrument request serialization/write, sidecar read/decode/dispatch/encode, and response read/decode phases so the code optimization targets the measured component. See the [report](../evaluation/completion/results/real-task-sprint/2026-10-28-python-bridge-repeated-calls.md), [full raw samples](../evaluation/completion/results/real-task-sprint/2026-10-28-python-bridge-repeated-calls-1-1000.json), and [1–100-call cohort](../evaluation/completion/results/real-task-sprint/2026-10-28-python-bridge-repeated-calls-1-100.json).

## Python bridge phase profile and native-image snapshot gate (2026-10-28)

- Added an opt-in `GUION_PYTHON_BRIDGE_PROFILE_OUT` diagnostic that separates first-call costs from repeated-call costs across Rust request serialization/write, response wait/parse/decode, and Python sidecar phases. Normal runs do not collect timers or attach profile data to bridge responses.
- The baseline profile attributed 0.220 ms per repeated call to full macOS dyld image enumeration, compared with 0.256 ms for Rust's end-to-end response wait. Repeated-call frame-read timing includes waiting for the next request and is not CPU attribution.
- The sidecar now takes a full snapshot after Python import or `ctypes.dlopen` audit events, or a changed dyld image count. Cached calls with no image change use only the count check (0.00080 ms per call). Dynamic `ctypes` library reporting still passes, including when the Python call raises.
- A separate 15-pair randomized cohort reduced the 1,000-call ratio from 4.131 (4.046–4.305) to 1.481 (1.439–1.559). Excess time per added Guion call fell from 0.2408 ms (0.2364–0.2542) to 0.0381 ms (0.0324–0.0442); these are separate cohorts, so the 84.2% decrease is descriptive rather than a paired estimate. One call remains around parity; Guion is still slower at 1,000 calls.
- The full runtime bridge suite passed 26/26; both CLI dynamic-image tests passed; the Python profile and frame checks passed 9/9. The feature-enabled release CLI built with two Cargo jobs. No VM or new dependency was used.
- Next, separate reader-thread wakeup and response-transport costs from Python execution before attempting that optimization.
