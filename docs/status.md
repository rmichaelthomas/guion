# Guion status

**Stage:** active development. The Guion-identity release matrix has passed on macOS ARM64 and Debian 12 GNU/Linux on ARM64 and x86_64, all with glibc. That cohort predates artifact format 44. Named current-format managed packages now pass on macOS ARM64 and Debian 12 ARM64 and x86_64. Feed Digest passes on macOS ARM64 and both Debian architectures: ARM64 natively and x86_64 under Rosetta. Broader package coverage remains open.

## What is established

- The default core CLI embeds a self-hosted compiler and runs on the Rust runtime. It can create, check, format, lint, test, run, build, package, verify, install, inspect, and document Guion programs.
- The current language includes typed functions and records, modules, collections, `Option`/`Result`, JSON, bounded file and HTTP operations, SQLite/TOML services, Unicode helpers, and bounded parallel work. The [language contract](../language/spec.md) is authoritative about what syntax works and what remains unsupported.
- New source, artifact, manifest, lock, and local-state names are `.gu`, `.gub`, `guion.toml`, `guion.lock`, and `.guion/`. A limited set of old Veritas project names remains readable during migration; see [compatibility](compatibility-and-migrations.md).
- The Guion-identity release matrix passed on macOS ARM64 and Debian 12 GNU/Linux on ARM64 and x86_64, all with glibc. This does not establish support for other operating systems, CPU architectures, or libc variants.

## Current evidence and its limits

- **CSV into columns (2026-11-12).** Artifact format 64 adds `csv_read_columns`, a native operation that reads a CSV file into typed columns. Streaming file reads (`csv_open`, `csv_next`, `file_open_lines` and `csv_read_columns`) no longer fail on a file larger than `max_file_bytes`. The `frames` reader is rebuilt on it: reading a 1M-row CSV took 0.21 s end to end against 2.81 s before, about 0.65 times pandas' time on one Apple M1 Pro (compute alone is still about 3 times pandas). The same batch cut the cost of calling a machine-code helper from interpreted code from about 7 µs to about 0.2 µs and made element-wise array maths reuse unshared buffers. See the [speed report](../evaluation/completion/results/2026-11-12-speed-report.md).
- **Data frames (2026-11-12).** Artifact format 63 adds array kernels for gathering, grouping and joining, and a first-party `frames` library (`packages/frames`, not yet published) builds data frames on them: CSV and JSONL reading, filtering, multi-key sort, group-by and joins. On one Apple M1 Pro against pandas 3.1.1 (15 interleaved, output-checked trials on a 1M-row CSV), every end-to-end workload took **5.3–8.1×** as long as pandas, because reading the CSV is about 45× slower (field parsing runs as guest code). After reading, Guion's sort was about 2.2× faster than pandas, the join about 1.6× slower, group-by about 4× and filter-and-sum about 11× slower. See the [data frames report](../evaluation/completion/results/2026-11-12-data-frames-report.md).
- **Native arrays (2026-11-11).** Artifact format 62 adds `Array[e]` n-dimensional arrays with checked conversions, broadcasting arithmetic, reductions, sorting and `matmul`, compiled identically by both compilers. On one Apple M1 Pro (15 interleaved, output-checked trials; NumPy 2.5.1, CPython 3.14.7), Guion took less time than plain CPython lists on every workload (ratios **0.032–0.660**). End to end it also took less time than NumPy on four of five plan-size workloads, mainly because NumPy's import costs about 52 ms. Estimated compute alone, Guion was slower than NumPy: about 2.1× on `a*b+c` over 10M elements, 1.3× on sum, 1.7× on sort and about 25× on 512×512 matmul at that time (since fixed in 8d73df4: about 2.8×). It was about 1.9× faster on a guest loop of `array_get`. A 10M-element elementwise run needs more than the default 256 MiB memory limit. See the [arrays report](../evaluation/completion/results/2026-11-11-native-arrays-report.md).
- **Speed gate on server CPUs (2026-11-03).** On GitHub's x86_64 (AMD EPYC 7763) and ARM64 (Neoverse N2) Linux runners, Guion took less time than the uv standalone CPython 3.14.7 on every lane of the text, JSONL and CSV gate, at 20,000 and 200,000 rows, from source and from artifacts (15 shuffled, output-checked trials per lane). The worst 95% upper bound of the Guion/Python ratio was **0.976** on x86_64 and **0.859** on ARM64; at 200,000 rows the median ratios were text 0.957–0.960 / 0.810–0.816, JSONL 0.860–0.897 / 0.844–0.855 and CSV 0.862–0.875 / 0.789–0.799 (x86_64 / ARM64). The x86_64 text margin is 3–4%, each host was measured once, and an Intel Xeon runner, which measured worse on an earlier build, has not been rerun. This closes the JSONL and CSV gaps recorded below for these workloads and hosts. See the [server speed-gate report](../evaluation/completion/results/real-task-sprint/2026-11-03-server-speed-gate.md) and the [task-class evidence](../evaluation/development/core_cost_closure/task-class-evidence.md).
- **Helper cost (2026-11-04).** Passing a list, map or text through a helper and storing the result back into the same variable used to copy the whole value on every call, so loops over such helpers cost the square of their size. A map helper over 10,000 keys took 10.941 s and now takes 0.043 s; 40,000 list appends took 9.212 s and now take 0.012 s; 160,000 text appends took 1.166 s and now take 0.032 s (one Apple Silicon Mac; see `evaluation/completion/results/2026-11-04-helper-cost-report.md`). A result stored in a different variable still copies, and functions that hand a list or map through a call run in the interpreter, not machine code.
- **Mac re-measurement (2026-11-05).** On main at commit `484cefd` (artifact format 61, macOS ARM64, CPython 3.14.7), Guion and Python each passed **127/127** frozen application cases, and seven-pair timing comparisons favored Guion in all nine selected everyday tasks (ratios **0.149–0.826**). ## Remaining product outcomes

The current-main checkpoint and named managed-package fixtures are complete on macOS ARM64; the 100,000-row analysis package passes on Debian 12 ARM64 and x86_64, and Feed Digest passes on macOS ARM64 and both Debian architectures. Current-format application packaging now includes both native-wheel data processing and pure-Python feed parsing. The Python bridge's 100,000-row comparison remains slower than both package-backed and standard-library Python in its latest cohort. Profiling repeated calls found an avoidable native-image scan; the event-gated observer reduced the 1,000-call bridge ratio from 4.131 to 1.481 and the excess per-call estimate from 0.241 ms to 0.0381 ms. Direct Python remains faster for this 1,000-call loop, so response transport and reader wakeup are the next performance target. The `readinto` change still halves isolated frame-read allocation; the direct-read fast path showed no measurable benefit and was reverted, and the streaming-reader prototype did not meet the memory bound. Broader package usefulness, bridge efficiency, and language learnability remain open. Historical recommendation exercises remain exploratory evidence, not a measure of broad adoption. See the [full outcome and raw data](../evaluation/development/core_cost_closure/results/sprint-20261029-jsonl-core-performance-outcome.md).

- The 2026-10-31 speed-closure sprint (branch `codex/guion-speed-closure`, artifact format 50) did not meet the JSONL speed gate. On the pinned Debian ARM64 container against PGO CPython 3.14.7 (9 interleaved, output-checked trials), the frozen program measured **1.35 / 1.29×** Python at 20k rows (source / artifact) and **1.49 / 1.66×** at 200k; the same logic written with the new fused `json_get_text_safe` / `json_get_int_safe` accessors and `format_utc_date` measured **1.24 / 1.10×** at 20k and **1.36 / 1.36×** at 200k (upper 95% bounds 1.14–1.40). The earlier 3–3.7× figures above predate the pool allocator, fat LTO and these accessors. A second workload, a CSV request ledger, measured **3.6×** Python at 200k rows; the lockfile-auditor holdout still leads Python (**0.33×** at 512 packages, **0.41×** at 2,048). Profiling shows the remaining gap is the interpreter's per-instruction cost (about 10 ns per integer instruction and 20–25 ns per data operation, with dispatch the largest share); the `Option`/`Result` box, CSV parser, limit-check and wrapper-inlining ideas were each worth under 8%, and a native tier owning `Text`/`List`/`Map` values is bounded at about 40% (CSV ledger ratio near 2.2), so it was not built. The claim the evidence supports is per task class: faster than CPython on short-lived, compute-bound and parallel CPU programs and on the lockfile-auditor holdout; slower on long interpreter loops over large row streams. The gate is open. See the [task-class evidence](../evaluation/development/core_cost_closure/task-class-evidence.md) and [raw paired data](../evaluation/development/core_cost_closure/results/jsonl-fused-vs-python-paired-9.json).

- The 2026-11-04 follow-ups (branch `feat/follow-ups`, artifact format 61) close most open items from Wave 1 and Track A. Chained text appends (`set s = s + a + b`) are now linear instead of hitting the allocation budget at about 60 KB; `std:random` runs on the machine-code path with unchanged sequences; functions returning `Unit` (including `fn main() -> Unit:`) and functions using `assert` now compile natively; `guion update` follows a registry package's recorded range; the registry and client support token rotation and revocation (`guion token rotate|revoke`); `guion check` requires hosts named in a library's URL literals to be declared; `fs_remove`/`fs_rename` act on symlinks themselves; and `std:net` adds mutual TLS. A sandbox escape through a dangling symlink was fixed. Records that hold scalar-only records now have a native layout, and a native-code defect that let a record kept across loop iterations be overwritten was fixed. Command-line programs are limited by memory in use rather than cumulative allocation and have no default instruction limit. The registry signs its log with ed25519 and the client verifies it. `guion check` and `guion inspect` say when a program can write files. Measured on macOS ARM64 with default limits: 1M random draws 5.57 s to 0.06 s (CPython 0.28 s); a 20M-iteration loop in a `Unit` main 0.61 s to 0.08 s (CPython 1.24 s). Not done: `.gub` attachments (deferred until separate compilation), deploying the updated Worker, and Linux results.
