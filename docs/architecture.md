# Architecture

Guion uses a Rust Cargo workspace with four crates. The CLI parses TOML manifests; the Python bridge uses `serde_json` for its framed protocol.

- `guion-model` owns source locations, diagnostics, mathematical integers, portable values including JSON trees and records, bytecode instructions, artifact encoding, and runtime errors.
- `guion-compiler` tokenizes and parses the complete entry module graph, checks type and export visibility, records per-module source IDs, and lowers functions into portable stack bytecode.
- `guion-runtime` validates artifact versions and control-flow stack heights, then executes with per-instance output, instruction, call-depth, integer, text, collection, file-size, and cumulative estimated-allocation limits. Format-16 artifacts carry schema-versioned source/dependency identities and build-time numeric ceilings; runtime uses the lower of each embedded ceiling and the host's `HostPolicy`. Allocation estimates cover guest data such as host inputs, collections, records, text/bytes/JSON, file/Python results, output rendering, and parallel work. They exclude interpreter/JIT frames, operand stacks, and scalar arithmetic temporaries so backend choice cannot alter the allocation-limit outcome; integer growth is bounded separately by the digit limit. File operations require an explicit root/read/write policy; canonical path checks block parent traversal and symlink escapes, though they do not create an OS sandbox.
- `guion-cli` exposes the same compiler/runtime path to a user.

The direction is `model <- compiler`, `model <- runtime`, and `compiler + runtime + model <- CLI`. Source compilation produces an `Artifact`; both the CLI and embedding API use `Runtime.load`, `Instance.invoke`, and `Instance.close`. The format is versioned and rejects malformed encodings; bytecode internals may change with a format version bump. Artifacts carry external Python declarations and calls. The CLI selects an exact interpreter from a managed project environment when its Python lock is present; embedding APIs and projects without managed Python still require an explicit interpreter path. The isolated Python sidecar explicitly adds the project root to its import path so typed adapters can live with project source while dependencies remain in the managed environment.

The optional Cranelift backend compiles eligible pure bytecode functions to host-native code. Straight-line bytecode shares a lowered block, and fuel is reserved for a whole bytecode block before that block executes. If the remaining instruction budget cannot cover the full block, native execution refunds its reservations and replays through the VM, preserving exact instruction-limit diagnostics; calls split the lowered blocks so a parent never holds fuel while a child runs. `run --json` reports eligible bytecode instruction and block-leader counts, actual Cranelift IR block/instruction counts, and per-function lowering, verification, and machine-code definition times. Bytecode leader counts exclude internal Cranelift guard and fuel-control blocks. Its current typed surface includes scalar `Int` and `Float64`, `List[Float64]` length/index reads, reads of supported numeric/list fields from records, same-local `list_set` updates, and record construction/return. Native list descriptors point into invocation-owned copies; this keeps caller values immutable and lets an updated record return its values without exposing Rust collection layouts to generated code. The verifier and type inference decide eligibility; unsupported operations stay on the VM. Checked list bounds and unsupported numeric cases deopt and replay through the VM so diagnostics and source traces remain authoritative. Native-to-native calls do not cross list-mutating functions, avoiding hidden alias changes. This is a growing execution subset, not a claim that every program is native.

The runtime supports bounded JSON parsing and serialization with exact integer numbers, sorted object keys, duplicate-key rejection, typed accessors and depth/byte ceilings. Parse, missing-key, and type errors are currently invocation errors.

The runtime's bounded `parallel_map` executes each task in an isolated VM instance on worker threads and returns `Result[List[U], TaskError]`. Each worker receives an initial item before workers share the remaining queue; this keeps short JIT-eligible tasks from all being claimed by whichever thread starts first. Workers preserve input order, use bounded worker allowances from the invocation's instruction and allocation budgets, stop scheduling and poll cancellation after failure, join running tasks, and merge completed output in input order. Eligible native code is compiled once by the caller and its immutable function-entry table is shared with workers; the parent retains the JIT module until every worker has joined. This avoids compiling the same artifact in every worker. `TaskError` retains the failed input index, runtime code, message and trace. Native call failures also retain their nested source call sites. Host setup and policy failures remain invocation errors. Immutable JSON and list values share reference-counted storage. A `set values = list_set(values, index, item)` assignment lowers to a copy-on-write local update: it reuses uniquely owned storage and clones when another value still aliases it, preserving observable immutability while avoiding repeated full-list copies in loops. Allocation charges are estimates at known guest-data creation points, not exact native memory measurements. `Runtime::vm_only()` provides a VM execution mode for deterministic backend diagnosis and comparison.

Embedders can pass a cloneable `CancellationToken` to `Instance::invoke_with_cancellation` and call `cancel()` from another thread. VM execution polls between instructions; JIT code polls at function entry and on backward branches; parallel workers share the invocation signal, stop taking work and are joined before cancellation returns. A running Python call polls at 20 ms intervals; cancellation kills and reaps the managed sidecar process. Synchronous HTTP cannot be interrupted while the blocking request is in progress, so cancellation is observed when that call returns or reaches its configured timeout. Completed file, network, Python, and output effects are not rolled back. The token is one-shot and should be newly created for each invocation. CLI Ctrl-C still terminates the process directly.

`Instance::effect_report()` retains ordered host-effect records for the most recent invocation, including captured output, file access, HTTP, environment reads, and Python calls. Records distinguish an operation that returned, returned an error, or was interrupted; they do not claim that a remote peer did or did not apply a request. The report is capped at 1,024 records, each target is capped at 256 Unicode scalar values, and `omitted_effects()` reports how many later records could not be retained. The CLI's `run --json` includes the same report and omission count.

The VM is a baseline for portability and inspection. A pre-rename Veritas JSON aggregation probe exposed and verified a quadratic collection-copy cost; after fixing it, that build reported lower median times than the Python standard-library version at 1,000, 5,000, and 10,000 rows on one Apple Silicon host, while its p95 was higher at 10,000 rows. These author-run measurements are a regression signal for one task, not general speed evidence for Guion. The accompanying worker test showed CPU-bound guest work on multiple OS threads on that host; it did not establish general speedup over Python. Guion-specific installed performance comparisons remain a pre-release task. Managed dependency resolution and the feed-digest application were also demonstrated in the historical Veritas build. Exact allocator/RSS accounting, a syntax-aware formatter, and broader comparative evaluation remain open parts of the north-star ambition.
