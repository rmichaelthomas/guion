# Running Guion in a browser

Guion programs can run in a browser through WebAssembly. This page describes what ships: the two modules, the call that runs an artifact, the version a host checks first, the limits, and what the browser VM does not do. The limit table is generated from the code and checked by tests, so the numbers here are the numbers the module enforces. The protocol source, with the request and response JSON Schemas, is `docs/browser-wasm-abi/` in the source tree.

## The two modules

| Module | Role | Source |
|---|---|---|
| `guion_compiler.wasm` | Compiles one in-memory `.gu` file (at most 65,536 bytes, no project imports) into `.gub` artifact bytes. It is a convenience adapter for single-file pages such as the playground and is not part of the browser ABI. | `site/tools/wasm-compiler` |
| `guion_vm.wasm` | Runs a `.gub` artifact on the same instruction loop as the native runtime (`guion-vm-core`), through the browser ABI described here. Built from `crates/vm-wasm`. | `crates/vm-wasm` |

A page that already has a compiled artifact needs only `guion_vm.wasm`. You can produce an artifact with `guion build FILE.gu` on a machine and ship the bytes. The VM module has no imports: a host instantiates it with an empty import object.

## ABI version and negotiation

`guion_wasm_abi_version() -> u32` returns `(major << 16) | minor`. This module implements ABI 1.0 and returns `0x0001_0000`. A host should call it first and refuse a major version it does not know. A module with no such export predates version discovery and offers only the legacy integer interface.

Every request carries an `abi` object, and the module accepts only the exact version it implements: any other `major` or `minor` returns `E_ABI_VERSION`. The ABI version is independent of the `.gub` artifact format number; the artifact format is checked when the artifact is decoded.

## Running an artifact: `execute_artifact_v1`

```text
execute_artifact_v1(artifact_ptr: u32, artifact_len: u32,
                    request_ptr: u32, request_len: u32) -> u32
result_response_ptr() -> u32
result_response_len() -> u32
```

1. Allocate one input buffer for the artifact and one for the request with `allocate_input(len)`, write the bytes into the module's memory, and call `execute_artifact_v1`. A zero from `allocate_input` means the length was zero or too large, or a live-input limit below was reached.
2. The return value is `0` for `ok: true` and `1` for a structured error. In both cases the JSON response is at `result_response_ptr()` for `result_response_len()` bytes. Copy it before the next call.
3. Release each input buffer with `release_input(ptr, len)`, using the exact pointer and length that `allocate_input` returned. A pointer or length that does not match a live buffer is `E_ABI_POINTER`.

The request:

```json
{
  "abi": {"major": 1, "minor": 0},
  "entry": "summarize",
  "arguments": [
    {"type": "Text", "value": "three notes"},
    {"type": "Int", "value": "3"}
  ],
  "capabilities": [],
  "limits": {"steps": 10000, "outputBytes": 65536}
}
```

`entry` names a function of the artifact (1 to 128 bytes); it does not have to be `main`. `arguments` are typed, tagged values: `Int` is a decimal string, `Float64` is 16 hexadecimal digits of IEEE-754 bits, `Bytes` is base64, and records, lists, maps, options, results and `Json` have their own tagged forms (see the SPEC). `capabilities` must be an empty array. `limits` is optional and may only lower the module's ceilings, with one explicit exception for the step budget (see "Raising the step budget"). Unknown request fields are rejected.

A success response:

```json
{"abi": {"major": 1, "minor": 0}, "ok": true,
 "value": {"type": "Text", "value": "..."}, "stdout": "", "steps": 12}
```

A failure has `ok: false`, a stable `code` and a readable `message`. A failure that comes from running the program (for example `R_STEP_LIMIT`) also carries `stdout` and `steps`. Branch on `code`, never on the text of `message`. The response JSON is the source of truth for a run; the legacy getters (`execute_artifact`, `result_output_ptr`, `result_return_value` and the rest) remain only for callers written before ABI 1.0 and return an `Int` result only.

Stable codes include `E_ABI_REQUEST`, `E_ABI_ARTIFACT`, `E_ABI_VERSION`, `E_ABI_ENTRY`, `E_ABI_VALUE`, `E_ABI_VALUE_UNSUPPORTED`, `E_ABI_LIMIT`, `E_ABI_POINTER` and `E_CAPABILITY_UNSUPPORTED`, plus the VM's own runtime codes such as `R_CALL_ARITY`, `R_CALL_TYPE`, `R_EXPORT_UNKNOWN`, `R_STEP_LIMIT` and `R_HOST_UNSUPPORTED`. Task, host-error and live native-resource values cannot cross the boundary and return `E_ABI_VALUE_UNSUPPORTED`.

## Limits

The effective limit of a run is the lowest of the request's `limits`, the module's ceiling and any limit embedded in the artifact.

## Raising the step budget

The default ceiling is `MAX_BROWSER_STEPS` (10,000 steps), and a request cannot go above it by default. A page that runs a bigger program, such as checking a beacon receipt, opts in per run:

```json
"limits": {"steps": 100000, "allowRaisedSteps": true}
```

With `allowRaisedSteps: true` the request's `steps` may be up to `MAX_RAISED_BROWSER_STEPS` (50,000,000), a hard ceiling that the option never moves. Without the option, or with `false`, a `steps` above 10,000 is `E_ABI_LIMIT` exactly as before, and a run that reaches its budget stops with `R_STEP_LIMIT`. The option leaves every other ceiling alone: output, allocation, artifact size (1 MiB) and the request size are unchanged. It is an additive request field on ABI 1.0; a module built before it rejects the unknown field with `E_ABI_REQUEST`, and the page can retry with the default budget. Choose `steps` as the program's measured cost with headroom, not the ceiling.

## Beacon cryptography and JSON in the browser

The pure cryptography of `std:crypto` and `std:encoding` runs in the browser VM, on the same code as the native runtime, with the same results and error codes (a test runs one set of vectors through both and compares them). Computation needs no grant, and nothing is fetched: a page passes recorded data in as program input (typed `Text` and `Bytes` arguments).

| Available in the browser | Functions |
|---|---|
| Hashes | `crypto_sha256`, `crypto_sha512`, `crypto_sha3_512`, `crypto_sha1` |
| Signatures and certificates | `crypto_rsa_verify` (PKCS#1 v1.5 and PSS), `crypto_ecdsa_p256_verify`, `crypto_bls12381_verify_g1`, `crypto_x509_rsa_public_key`, `crypto_x509_verify_issued_by`, `crypto_pem_decode` |
| Timelock (drand tlock, age format) | `crypto_tlock_decrypt`, `crypto_tlock_round`, `crypto_tlock_chain_hash`, and encryption through `native_crypto_tlock_encrypt` when the caller supplies the 48 bytes of randomness |
| Encoding | `dagcbor_encode`, `hex_encode`/`hex_decode`, `base64_*`, `bytes_xor_key` |
| Bit operations | `int_and`, `int_or`, `int_xor`, `int_shift_left`, `int_shift_right` (64-bit; `R_INTEGER_RANGE` and `R_SHIFT_RANGE` as natively) |
| JSON | `json_parse`, `json_stringify`, `json_get`, `json_index`, `json_has`, `json_len`, `json_set`, `json_push`, the `json_as_*` and `json_try_*` accessors and the JSON constructors, with native limits and error codes |

Not available, and failing with `R_HOST_UNSUPPORTED` when reached: **HMAC** (`crypto_hmac_sha256`, `crypto_verify_hmac_sha256`) and **random bytes** (`crypto_random_bytes`, `crypto_random_hex`, `crypto_random_base64url`) stay native-only. The wrapper `crypto_tlock_encrypt` draws its randomness with `crypto_random_bytes`, so it is not available in the browser; `crypto_tlock_decrypt` is. A page that must seal a file supplies randomness itself (from `crypto.getRandomValues`) to `native_crypto_tlock_encrypt(round, chain_hash, public_key, plaintext, randomness)`. The column and projection instructions of the JSON data library (`json_int_column`, `json_project_columns` and their kin) and `json_stringify_pairs` also remain native-only.

The beacon package (`packages/beacons`: drand, tlock, Twine/CURBy and NIST) checks a recorded receipt in the browser. One program that verifies a drand round, opens a tlock file, verifies a CURBy-Q pulse and verifies two NIST pulses with their precommitment chain, all from embedded data, was measured at **167,349 bytes** of artifact (limit 1 MiB) and **34,008 steps** (default budget 10,000), so it runs with `allowRaisedSteps` and a budget of 100,000 steps. `cargo test -p guion-vm-wasm --test crypto` runs it and records both numbers.

## Capabilities: none

ABI 1.0 grants no capabilities. `capabilities` must be `[]`; any other value returns `E_CAPABILITY_UNSUPPORTED` before the artifact runs. The browser VM runs the same instruction loop as the native runtime, but it has no host behind it. Computation, calls, records, lists, maps, text, JSON, the beacon cryptography below and `print` to standard output work. An operation that needs the host fails when it is reached with `R_HOST_UNSUPPORTED`, and the message names the operation (for example `host operation `ReadText` is not available in this environment`). The five classes of host operation that are always unavailable are:

1. filesystem (`read_text`, `fs_*`, file readers and writers)
2. network (HTTP, sockets, TLS)
3. database (SQLite)
4. clock (the current time and date)
5. process (running programs, standard error output, and the rest of the process surface)

Other host-backed operations that the portable host does not implement fail the same way. The module does not inherit permissions from `guion.toml` or the command line, and nothing is skipped silently.

## What the browser VM does not have

- **No DOM.** A Guion program cannot read or change the page. The host page reads the response and does the drawing.
- **No events.** There are no callbacks, timers or listeners. A run is one synchronous call from entry to result.
- **No JavaScript imports.** The module declares no imports; it cannot call into the page, and the page cannot hand it functions.
- **No in-browser grants.** There is no way to grant a file root, a network host or a clock from the page. A non-empty `capabilities` list is an error, not a request.
- **No `parallel_map`.** It needs threads, and the browser VM has none: it fails with `R_HOST_UNSUPPORTED` naming `ParallelMap`. Everything else that takes a function runs: `map_list`, `try_map_list`, `filter_list`, `fold_list`, `any_list` and `all_list` (all `HigherOrder`) accept closures that capture variables, and `sort` (`SortNatural`), `sort_by` (`SortByKey`, or `SortBy` with a comparator), `sort_by_int_key` (`SortByIntKey`) and `merge_sorted_by_int_key` (`MergeSortedByIntKey`) order values exactly as the native runtime does, with the same instruction and allocation charges. As natively, a sort takes a named function or a literal that captures nothing; a closure passed to one is `R_FN_CLOSURE`. Use a `for` loop in place of `parallel_map` in code meant for the browser.
- **No source compilation in the ABI.** The VM runs artifacts only. Compiling source in the browser is the separate `guion_compiler.wasm` adapter above.
- **No persistence.** Nothing survives between calls except what the host keeps itself.

## Checking the claims

`cargo test -p guion-vm-wasm --test browser_docs` asserts the ABI version, every number in the limit table, the host-operation statements and the function-value statement above against the code. `cargo xtask browser-docs --check` (also run by `cargo xtask agent-reference --check`) fails when the table differs from the constants, and `cargo xtask browser-docs --write` regenerates it.
